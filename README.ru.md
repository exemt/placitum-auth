# Placitum auth

[English](README.md) · Русский

Проверка входа перед приложением. Приложение продолжает проверять своих пользователей само;
Placitum добавляет ещё одну проверку — ту, которую администратор задал в профиле: одноразовый код,
список логинов и паролей, LDAP, NTLM, токен чужого издателя или вход самого приложения. Для
пользователя это второй фактор, для приложения — обычный заголовок с именем вошедшего.

Для модуля nginx это обычный инспектор, который отвечает `allow`, `redirect` или `deny`.

## Два процесса, один образ

| | Инспектор (`auth`) | Форма входа (`auth-http`) |
| --- | --- | --- |
| Где живёт | шина, `waf.req.auth`, queue group | `location` формы в nginx, `proxy_pass` |
| Когда вызывают | на каждом запросе маршрута | только вход, выход и продление |
| Бюджет | около 20 мс | сотни миллисекунд: bcrypt, LDAP, контроллер домена |
| Ответ | вердикт: `allow`, `redirect`, `deny` | HTML формы, `Set-Cookie`, 303 назад |
| Состояние | проверка токена, зеркало набора в памяти | Redis: nonce, попытки |
| Падение | политика `waf_deadline` маршрута | новые сессии не выдаются, действующие живут |

Проверка пароля обязана быть медленной по построению, поэтому держать её в процессе, у которого
20 мс на весь трафик маршрута, нельзя. Третий бинарь, `auth-probe`, — проверка здоровья
инспектора.

## Решение

```
waf_sid открылся, срок не вышел, привязка совпала, сессия есть в списке
                                          → allow + заголовки приложению
токена нет или он не принят,
    метод в redirect_methods и это навигация  → redirect 303 на login.uri
    иначе                                     → deny response=auth_required (401)
```

Редирект на страницу входа осмыслен только там, где ответ увидит человек в браузере. `POST`,
`PATCH`, `DELETE` и любой `fetch` при 303 теряют тело, поэтому им — 401 с машиночитаемым телом, и
клиент сам решает, показывать ли форму. На собственном `login.uri` проверка входа отвечает `allow`
(`AUTH_SELF`), так что вход никогда не требует входа.

## Провайдеры

Один профиль — один провайдер. Комбинации вроде «пароль плюс TOTP» — это две проверки входа на маршруте;
проверка входа TOTP берёт пользователя из сессии первой (`identity.from`).

| Провайдер | Что доказывает | Где считается |
| --- | --- | --- |
| `local` | пароль из набора пространства | bcrypt в процессе формы |
| `code` | секрет TOTP (после другой проверки входа) или общий код доступа | HMAC, локально |
| `ldap` | пароль в каталоге | bind к LDAP: `upn`, `dn_template` или `search` |
| `ntlm` | пароль в домене Windows | NTLM-bind к контроллеру домена по LDAP |
| `jwt` | токен чужого издателя в куке или заголовке | подпись и claims, без формы |
| `app` | вход самого приложения | проверка входа смотрит, что приложение приняло вход, и доверяет его куке |

`ldap` и `ntlm` — Платные функции по [лицензии](LICENSE.ru.md): для них нужна Коммерческая лицензия.
На оценку даётся 30 дней, образовательным организациям они бесплатны.

Пользователи `local` — обычный набор строк `login:bcrypt[:группы[:ссылка на секрет TOTP]]`,
правится как любой другой набор, включая срок у записи. Пароли служебных учёток и секреты TOTP —
ссылки на объекты хранилища (`password_store`), которые форма открывает ключом установки;
`password_env` вместо этого берёт пароль из переменной окружения, и оба сразу в профиле быть не
могут.

## Сессия

```
waf_sid = "s3." + base64url(nonce || AES-256-GCM(payload))
```

Токен запечатан, а не подписан: логин и группы не видны ни клиенту, ни в журнале прокси. В нём
идентификатор сессии, субъект, время выдачи, срок, точка продления, источник, выдавший сессию,
привязка к подсети клиента (`/24` для IPv4, `/64` для IPv6) и отпечатку User-Agent, пройденные
факторы и группы. Профиль принимает токен только своего источника.

### Кука и список

Кука доказывает, что сессию выписали мы; запись в активном наборе — что её не
завершили. На каждом запросе старше грейса инспектор сверяет идентификатор сессии со своим
зеркалом набора: запись есть — `allow`, записи нет — `deny` с `AUTH_SESSION_REVOKED` (навигации —
форма), списка не видно — `error` с `AUTH_LIST_UNAVAILABLE`. Удаление записи — единственный способ
завершить сессию снаружи: выход на форме, кнопка в панели и скрипт разбора инцидента делают одно и
то же. Повод записи несёт логин (`AUTH_LOGIN operator`), и набор читается как список вошедших.

### Продление

На `allow` модуль куку не ставит, поэтому скользящего срока нет. После
`renew_after` инспектор перенаправляет навигацию на `<login>/renew`, и форма перевыпускает токен, не
спрашивая пароль; `renew_after: 0` механизм выключает. Продление не бесконечно:
`session.max_ttl` — предельный срок сессии от входа вместе с продлениями (`0` — без предела), а
пользователю `local`, которого удалили, выключили или которому сменили пароль, форма сессию не
продлевает.

### Попытки

Билет входа одноразовый, неудачи считаются в Redis и по адресу, и по логину; слишком
много в окне — вход блокируется на время. Попытка считается до проверки пароля, поэтому
параллельные отправки лишних попыток не дают; адреса IPv6 считаются по /64. Блокировка по адресу
общая на все профили процесса. Число одновременных проверок пароля ограничено
`WAF_AUTH_VERIFY_LIMIT`.

## Заголовки приложению

На `allow` инспектор выставляет заголовки запроса: `X-WAF-User` (субъект), `X-WAF-Groups` (группы
через запятую) и `X-WAF-Auth` (пройденные факторы, например `ldap+totp`). Имена задаются в секции
`upstream` профиля. Заголовки выставляются всегда, даже пустыми: копировать заголовки запроса модуль
не умеет, и перезапись — единственный способ обезвредить `X-WAF-User`, присланный клиентом. На
маршрутах без проверки входа приложение этим заголовкам доверять не должно; очистите их в nginx:

```nginx
proxy_set_header X-WAF-User "";
```

Пользователя приложение может прочитать и само — из куки `waf_id`, запечатанной отдельным ключом
приложения (`WAF_AUTH_APP_KEY_FILE`). Ключ установки приложению не отдают никогда: с ним оно
выпишет себе сессию мимо второго фактора. Соседним инспекторам пользователь передаётся секцией `sessions` в
сообщениях следующих волн, а не заголовками.

## На маршруте

Маршрут обязан копировать заголовки и не маскировать `cookie`, иначе инспектор видит sha256 вместо
токена и перенаправляет вошедших на форму. Проверки входа ставят на разные волны, в порядке
`challenge`, `captcha`, `auth`, потому что два редиректа в одной волне гоняются друг с другом. Баллов
`auth` не даёт: его ответы — `allow`, `redirect` и `deny`.
